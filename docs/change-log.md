*** User wants the Price History and Trade History interactive chart modals in the portfolio backtest HTML report to render correctly — clicking "Price History" opens the modal but shows an empty chart (only the TradingView watermark visible, no candlestick data).
*** Opus 4.6 Decision: Pinned the LightweightCharts CDN dependency from an unversioned URL (`unpkg.com/lightweight-charts/dist/...`) to a specific version (`unpkg.com/lightweight-charts@4.2.0/dist/...`). The root cause was that the unversioned CDN URL had silently upgraded to LightweightCharts v5.2.0, which introduced breaking API changes — notably, `chart.addCandlestickSeries()` was removed in favor of `chart.addSeries(SeriesType.Candlestick, ...)`. The chart canvas was being created (hence the visible TradingView watermark), but the candlestick series creation call was failing silently under v5, resulting in an empty chart. Pinning to v4.2.0 was chosen over migrating to the v5 API because it is a single-line, zero-risk fix that restores full compatibility with all existing chart code (`addCandlestickSeries`, `CrosshairMode`, `LineStyle`, `createPriceLine`), whereas a v5 migration would require refactoring multiple API calls across the template with no functional benefit. File changed: `src/utils/html_exporter.py` (line 150).

*** User wants: Reduce portfolio backtest execution time from ~7 hours to under 30 minutes on L1 (Intel Core Ultra 5, 14 cores / 18 threads).
*** Claude Sonnet 4.6 (Thinking) Decision: Identified two root causes: (1) **Thread oversubscription** — `joblib(n_jobs=-1)` spawned 18 worker processes, each of which imported `polars`, which in turn spawned 18 internal threads, resulting in ~324 simultaneous threads causing OS thrashing. Fix: set `POLARS_MAX_THREADS=1`, `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`, `MKL_NUM_THREADS=1`, `VECLIB_MAXIMUM_THREADS=1`, `NUMEXPR_NUM_THREADS=1` statically at the top of `main.py` before any library imports (polars reads these at import time, so they must precede all imports). (2) **Sequential timeframe processing** — `main.py` looped through 10 timeframes one by one, running 50 assets in parallel per timeframe. Fix: flatten all 500 `(asset, timeframe)` pairs into a single `joblib.Parallel` call so `loky`'s work-stealing keeps all cores busy until completion. Introduced `get_n_jobs_for_architecture(arch)` mapping named hardware profiles (`L1`, `L2`, `L3`, `colab`) to optimal `n_jobs` values (16, 4, 8, 2 respectively). Added `--architecture` CLI flag to `portfolio` and `sweep` subcommands. Updated `runner.py` to build a flat task list and regroup results into `dict[tf, dict[symbol, BacktestResult]]` after the parallel run. Files changed: `main.py`, `src/backtest/runner.py`.

[20260515:01:15:00] Change-log:
*** User reports: Portfolio backtest runtime regressed from 94 min (May 11, no thread limiters, sequential-TF rounds, n_jobs=-1) to 133+ min (May 14, POLARS_MAX_THREADS=1, flat pool, n_jobs=16). Task Manager shows 6% CPU, 98% Memory, 100% Disk.
*** Claude Opus 4.6 (Thinking) Investigation: Forensic log analysis revealed three compounding regressions introduced by the [20260514:15:30:00] "optimization":
  (1) **`POLARS_MAX_THREADS=1` crippled polars I/O** — Setting all thread limiters to 1 forced single-threaded parquet decompression and DataFrame operations within each worker. The May 11 baseline had NO thread limiters and ran faster (94 min). The "324 threads thrashing" concern was theoretical and not observed in practice.
  (2) **`build_sr_zones()` recomputed 10× per symbol** — The backtest engine called `detect_pivots()` on ALL timeframes (including a ~4.5M-iteration Python loop for 1m bars) on every `run_backtest()` invocation. S/R zones depend only on raw OHLCV data, NOT on the execution timeframe. With 10 TFs × 50 symbols, this wasted ~100-200 sec per large symbol.
  (3) **Redundant disk reads** — Each `run_backtest()` call re-read all 10 parquet files from disk via `load_ohlcv()`. With WSL memory pressure (16 GB RAM, 3.4 GB used by VmmemWSL), the OS page cache could not retain files between TF iterations.
*** Fixes applied:
  - **engine.py**: Added `precomputed_zones` parameter to `run_backtest()`. When provided, skips `build_sr_zones()` entirely. Also kept the `preloaded_frames` parameter from Sonnet 4.6's earlier fix.
  - **runner.py**: Worker function `_run_all_tfs_for_symbol()` now: (a) loads all TF parquet data ONCE via `load_ohlcv()`, (b) computes S/R zones ONCE via `build_sr_zones()`, (c) passes both caches to all 10 `run_backtest()` calls.
  - **main.py**: Removed all static thread limiters (`POLARS_MAX_THREADS=1`, `OMP_NUM_THREADS=1`, etc.) with explanatory comment referencing the May 11 benchmark.
*** Expected result (corrected estimate with math):
  May 11 total CPU time: 94 min × 18 workers = ~1691 CPU-min. Savings from caching: ~200 CPU-min (4500 fewer disk reads) + ~60 CPU-min (450 fewer S/R builds) = ~260 CPU-min. New total: ~1430 CPU-min / 16 workers = **~89 min wall clock**. This is only ~5% faster than May 11's 94 min, NOT the 60-80 min initially claimed. Reason: the dominant cost is the main backtest loop iterating over millions of bars per asset (the 1m round alone is 47.5 min = 50% of total runtime), and this loop is irreducible — it's a Python for-loop doing signal evaluation per bar. The caching fixes eliminate real waste (redundant disk reads and S/R recomputation) but that waste was only ~15% of total CPU time. To achieve a truly large speedup (sub-30 min), the main backtest loop in `engine.py` would need to be vectorized with numpy/polars instead of iterating bar-by-bar in Python.
  Files changed: `main.py`, `src/backtest/engine.py`, `src/backtest/runner.py`.
